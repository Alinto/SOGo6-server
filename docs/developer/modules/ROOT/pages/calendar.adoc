= Calendar Module

The calendar module manages calendars and events stored in the database or fetched from external ICS feeds.
It is built around two domain objects — `CalCalendar` and `CalEvent` — that flow through sources, repositories, RRULE expansion, and serializers without any format leaking across layers.

== Architecture overview

----
  Data sources                    Consumers
  ─────────────                   ─────────
  Database (sogo_events)          REST API (JSON)
  Remote ICS URL                  CalDAV server (ICS)
         │                               │
         ▼                               ▼
   CalendarSources (factory)       Serializer (JSON / ICS)
         │                               │
   CalendarSource (pipeline)            │
         │                              │
         └──────── list[CalEvent] ──────┘
----

`ModuleCalendar` is the single entry point for all business logic.
It delegates source resolution to `CalendarSources`, which returns the right `CalendarSource` implementation for each calendar.

== Domain model

`CalEvent` (`app/module/calendar/model/CalEvent.py`) is the single canonical representation of a calendar component (VEVENT, VTODO or VJOURNAL).
It is a plain Python dataclass with no dependency on any serialization format.
The `component_type` field (`EVENT`, `TASK`, `JOURNAL`) discriminates between component kinds stored in the same table.

Fields are either *relational* (stored as dedicated columns for filtering: `date_start`, `date_end`, `component_type`, `show_as`, `rrule`, `is_deleted`, `recurrence_id`) or *blob* (everything else, stored as JSON in `cal_event`).
`calendar_key` and `calendar_timezone` are set by the source layer at query time and never persisted in the blob.

`CalCalendar` (`app/module/calendar/model/CalCalendar.py`) maps to the `sogo_calendars` table.
The `source_type` field (`'local'`, `'ics'`, `'caldav'`) drives dispatch in `CalendarSources`.
`ctag` is incremented on every event mutation and used by CalDAV clients to detect changes without fetching the full event list.
External sync metadata (URL, credentials, etag) lives in the `sync_config` JSON column, which is `NULL` for local calendars.

All datetime values in the module are stored and processed in UTC.
Naive datetimes are assumed UTC. The original TZID is preserved in `CalEvent.timezone` for display purposes only.

== Calendar sources

`app/module/calendar/source/`

`CalendarSource` is an abstract base class that defines a fixed processing pipeline.
Subclasses implement `_fetch_events()` (and optionally `_fetch_tasks()`); everything else is handled by the base class.

`get_events(start, end, search)` runs:

. Resolve and normalize bounds to UTC
. `_fetch_events()` — subclass fetches raw events
. `_expand_recurring()` — RRULE expansion (see below)
. `filter()` — date range check + optional full-text search
. Sort ascending by `date_start`
. Stamp `calendar_key` and `calendar_timezone` on each event

The Python filter step after expansion is necessary: the DB pre-filters recurring *series* by `date_end_recurrence`, but individual occurrences generated by expansion must still be checked against the exact requested bounds.

Two source implementations exist:

* `CalendarSourceDb` — backed by the local database. Writable (full CRUD). On event insert, `date_end_recurrence` is pre-computed for recurring events to enable SQL-level filtering. Soft-deletes only (`is_deleted = True`) — events are never hard-deleted, which is required for CalDAV sync reports.
* `CalendarSourceIcs` — read-only, backed by a remote ICS URL fetched on every call. Size is capped at 10 MB; requests time out after 10 s. URLs are validated at construction time to reject private/loopback addresses (SSRF protection).

`CalendarSources` (`app/module/calendar/source/CalendarSources.py`) is the factory and the ownership enforcer.
All reads are always scoped to a `user_uid`. It merges events from all user calendars when no `calendar_key` is specified.

== Recurrence — RruleEngine

`app/module/calendar/rrule/RruleEngine.py`

`RruleEngine.expand()` expands a recurring master event into a flat list of occurrences within a date window.
It segregates singles, masters, and detached overrides (events with `recurrence_id`), generates dates from the RRULE, suppresses EXDATE entries, replaces overridden occurrences, and clones the master for each remaining date.

`get_max_date(master)` returns the end of the last occurrence (or `None` for unbounded series) and is used to populate `date_end_recurrence` in the database.

== Repositories

`app/module/calendar/repository/`

Repositories are the only classes that issue SQL.
`RepositoryCalendar` handles reads and writes for `sogo_calendars`.
`RepositoryEvent` handles reads and writes for `sogo_events`.

All queries use structured `Condition` objects translated by `ClientSQL` to parameterized statements — no string interpolation.
The `find_by_calendar` method applies two different SQL conditions depending on whether an event is recurring or not: non-recurring events are matched on `date_start`/`date_end`; recurring events are matched on `date_start`/`date_end_recurrence` to pre-filter at series level before in-memory expansion.

== Serialization

`app/module/calendar/serializer/`

Two formats are supported:

* *ICS (RFC 5545)* — `CalendarEventsDeserializerIcal` parses a VCALENDAR into a list of `CalEvent`. `CalendarEventSerializerIcal` produces VCALENDAR text. The `icalendar` library is used here and *only* here.
* *JSON (REST API)* — `CalendarEventSerializerJson` / `CalendarEventDeserializerJson` convert between `CalEvent` and flat dicts. `CalendarEventsSerializerJson.to_response()` wraps the list with a `total_count` field.

== Module — ModuleCalendar

`app/module/calendar/ModuleCalendar.py`

`ModuleCalendar` contains all business logic and is instantiated per request.
It exposes calendar CRUD, event CRUD (VEVENT), and task CRUD (VTODO).

On event delete, it dispatches to `delete_detached_occurrence` when `recurrence_id` is set (soft-deletes the occurrence row and adds the date to the master EXDATE), otherwise deletes the master and all its detached rows by UID.

Every mutation calls `_bump_ctag` to increment the calendar's `ctag`.

`get_events` and `get_tasks` enforce a maximum date range of 31 days unless a search query is present.
