= DAV Server

The DAV server exposes calendars and address books to standard clients (Apple Calendar and Contacts, Thunderbird, DAVx5...) over WebDAV, CalDAV (RFC 4791) and CardDAV (RFC 6352).
It runs as a separate process, deployable in its own container: heavy clients keep long sessions and sync often, and this load must not slow down the REST API used by the web interface.

The server reuses the business modules of the REST API (xref:calendar.adoc[], xref:contact.adoc[]); only the protocol layer is specific to DAV.

== Architecture overview

----
  Client (CalDAV / CardDAV)
       |
       v
  DavApp (WSGI, Flask)          only file depending on Flask
       |  DavRequest
       v
  DavDispatcher                 configuration check, method -> handler, error -> HTTP status
       |
       v
  DavHandler.handle             DavAuthenticator: Basic credentials -> DavContext, then process()
       |
       +-- DavOptionsHandler    OPTIONS
       +-- DavPropfindHandler   PROPFIND
       +-- ...                  one handler per HTTP method
       |
       v  DavResponse
  DavApp -> WSGI response
----

**Responsibilities:**

* *build_app* - Builds the application for both launchers, like the REST API: initialises the worker (configuration state, cache, agent client), creates the authenticator, the handlers and the dispatcher.
* *DavApp* - Converts each Flask request into a `DavRequest`, hands it to the dispatcher and converts the `DavResponse` back. Redirects the well-known URIs. Turns off the Flask behaviours meant for web applications (see below).
* *DavDispatcher* - Routes a request to the handler of its HTTP method. Answers 503 while SOGo is not configured, and the HTTP status of the error when the handler raises a `RequestException`, authentication included. A 401 always carries the Basic challenge, and an error tied to a condition of the protocol an XML body naming it (see <<error-bodies>>).
* *DavAuthenticator* - Checks the Basic credentials of a request and builds its `DavContext` (see <<Authentication>>).
* *DavLoginLimiter* - Counts the wrong passwords of each login in Redis and blocks the login once the limit of its domain is reached (see <<login-blocking>>).
* *DavContext* - Configuration, user and cache client handed to `process` for one request: the DAV counterpart of Flask `g` in the REST API.
* *DavHandler* - Abstract handler of one HTTP method. Its `handle` method, which handlers cannot override, gets the cache client of the worker, authenticates the request then calls `process`, the method each handler implements. Handlers only see `DavRequest`, `DavContext` and `DavResponse`, never Flask, so they are tested without a WSGI layer.
* *DavOptionsHandler* - Answers OPTIONS with the `DAV` compliance classes and the `Allow` methods.
* *DavPropfindHandler* - Answers PROPFIND with the properties of the resources (see <<PROPFIND>>).

The DAV server never imports the REST layer (`app.api`): no Smorest, no JSON middleware, no `ApiBaseResponse`.

=== Layers compared with the REST API and the Agent

The DAV server follows the same layers as the other entry points (xref:1_4_archi_interfaces.adoc[], xref:agent.adoc[]).
A handler deals with the protocol of one HTTP method (XML, `Depth`, `If-Match`, multistatus) whatever the resource targeted; the glue between modules and serializers lives in the `InterfaceDav*` classes, one per domain, next to the `InterfaceApi*` and `InterfaceAgent*` ones in `app/interface/<domain>/`.

----
  Flask (DavApp)
       |
       v
  DavDispatcher        method -> handler, error -> HTTP status
       |
       v
  DavHandler.handle    authentication: DavAuthenticator, Basic credentials -> DavContext
       |
       v
  DavHandler.process   protocol of the HTTP method: body, Depth, multistatus
       |
       v
  DavResource          resource of the path, found by DavResourceResolver: properties, members
       |
       v
  InterfaceDav*        glue between the modules, in app/interface/<domain>/
       |
       v
  Module*              business logic
----

The handler never calls an interface: it does not know whether the path targets a principal, a calendar or a contact, and asks the resource (see <<Resources>>).
A resource never calls a module or a manager: it reads the authenticated user of the `DavContext`, loaded by `InterfaceAuthUser` during the authentication, or calls the `InterfaceDav*` of its domain.
The resolver builds `InterfaceDavCalendar` and calls it to find a calendar; the home of the calendars calls it to list the calendars. The root and the principal only read the user and hand the interface down to their members. The address books are not served over DAV yet.

== Routes

[cols="1,3"]
|===
| Path | Behaviour

| `/dav/` and below
| The methods of `DAV_METHODS` (`app/dav/DavConst.py`) are forwarded to the dispatcher. Any other method is answered 405 with an `Allow` header listing them.

| `/.well-known/caldav`, `/.well-known/carddav`
| 301 redirect to `/dav/` whatever the method (RFC 6764 section 5). The redirect is sent with `Cache-Control: no-cache`, so that clients follow the DAV root if a deployment moves it.
|===

`DAV_METHODS` lists the methods served, each one by its own handler: it feeds the routes, the `Allow` header of OPTIONS and of 405 responses. Serving a new method means adding its handler in `build_app` and the method to `DAV_METHODS`; a unit test checks that both match.

The path given to the handlers is relative to `/dav/` and percent-decoded: `/dav/alice%40example.org/` reaches them as `alice@example.org/`.

== Resources

A path below `/dav/` targets a resource of the DAV tree of the account of the request. The tree only holds the resources of that account: the other accounts are neither listed nor reachable.

----
  /dav/                              DavRootResource             member: the principal of the account
  /dav/<account>/                    DavPrincipalResource        members: the two homes
  /dav/<account>/Calendar/           DavCalendarHomeResource     members: the calendars of the user
  /dav/<account>/Calendar/<name>/    DavCalendarResource         calendar, read only, without member yet
  /dav/<account>/Contacts/           DavAddressBookHomeResource  home of the address books
----

`<account>` is the login of the Basic authentication, followed by `!<alias>` for an account signed in with an alias (see <<account-alias>>).
`<name>` is `personal` for the default calendar (`DAV_DEFAULT_COLLECTION`, given by the resolver to `InterfaceDavCalendar`, which names the calendars) and the key of the calendar for the other ones: SOGo 5 named the default calendar `personal`, and the clients of an account set up on SOGo 5 keep their URLs (see <<calendars>>). The address books are not served over DAV yet.

* *DavPath* - Builds the paths of the tree of an account, from its user and the alias of its login, and normalizes the paths of the requests to compare them: the only class knowing the layout of the URLs. A normalized path ends with `/` and has no empty segment. Its account is read as the Basic login: the domain is case-insensitive, the local part is not, and the alias is kept as is.
* *DavResource* - Abstract resource of an account, built with the user and the alias of its login, and with the interface a resource needs to list its members: its path, its properties by name (`properties()`), and its members (`children()`), listed by a PROPFIND with `Depth: 1`. `properties()` gives the properties of every resource, `resourcetype` and `current-user-principal`, followed by the own properties of the resource.
* *DavPrincipalResource* - The principal of the account (RFC 3744), which is also the collection holding the two homes. Its properties are the paths of the account, `principal-URL` and the homes of its calendars and address books (`calendar-home-set`, `addressbook-home-set`), followed by the properties converted from the user by `UserSerializerDavProps`.
* *DavCalendarHomeResource*, *DavAddressBookHomeResource* - The homes; their only own property is their name (`displayname`). The home of the calendars lists the calendars of the user through `InterfaceDavCalendar`.
* *DavCalendarResource* - A calendar of the user (see <<calendars>>).
* *DavResourceResolver* - Finds the resource of a path among the paths of the account, and builds it from the `DavContext` and `InterfaceDavCalendar`. Any other path, of another user or another alias included, is answered 404 (`ERROR_DAV_RESOURCE_NOT_FOUND`), which does not disclose whether the account exists.

[[calendars]]
=== Calendars

The home of the calendars lists all the calendars owned by the user, whatever their source (local, ICS or CalDAV subscription), through `InterfaceDavCalendar.get_all_calendars`.
The calendars shared by other users are not listed, and their keys are not found: the interface asks the module for the calendars the user owns only (`ModuleCalendar.get_all_owned_calendars`, which does not read the shares), and looks a name up among the listed calendars only (`InterfaceDavCalendar.get_calendar`). Listed, a default calendar shared by another user would take the path of `personal`, held by the default calendar of the user.

The default calendar is listed as `personal`, as on SOGo 5: DAVx5 and the Apple clients read the home again at each sync, and a calendar found under another name would be deleted and created again on the device. A request may also name it by its key, and gets the path it asked for. The name is case-sensitive.

The resource gives the `resourcetype`, `collection` and `calendar` (RFC 4791 section 4.2).
The properties of a calendar are converted by `CalCalendarSerializerDavProps` (see <<business-model-properties>>):

* `displayname`, `calendar-description` (when set) and the Apple `calendar-color` (when set).
* `getctag` of CalendarServer - the `ctag` of the calendar, changed with every object of the calendar: clients compare it before syncing.
* `supported-calendar-component-set` - `VEVENT` and `VTODO` (`DAV_CALENDAR_COMPONENTS`).

`InterfaceDavCalendar` adds:

* `calendar-timezone` - the time zone of the calendar, as a VCALENDAR holding its VTIMEZONE alone (RFC 4791 section 5.2.2), written by `CalCalendarTimezoneSerializerIcal` of the calendar module: the DAV server does not write iCalendar itself. An unknown time zone is written as UTC. The VTIMEZONE of a time zone is built once per process.

`DavCalendarResource` adds:

* `supported-privilege-set` (RFC 3744 section 5.3) - `read`, which aggregates the `read-free-busy` privilege of CalDAV (RFC 4791 section 6.1.1).
* `current-user-privilege-set` (RFC 3744 section 5.4) - `read` and `read-free-busy`, an aggregate privilege being listed with the privileges it holds. The calendars are not written over DAV yet: clients show them read only instead of failing on each change.

OPTIONS does not announce `calendar-access` yet: it promises every requirement of CalDAV (RFC 4791 sections 2 and 5.1), among which the calendar reports, the ETags and `supported-report-set`. It is announced once they are served. Thunderbird does not need it to add a calendar.

[[account-alias]]
=== Account alias: one address book per account (macOS Contacts)

macOS Contacts syncs a single address book per CardDAV account and picks it through its own discovery: it ignores the principal URL of a configuration profile, follows `current-user-principal`, and tells its accounts apart by login.
To sync several address books, the user adds one account per address book, with the login `<login>!<alias>`, `<alias>` being the key of the address book.

The authentication, the paths and the resolution handle the alias as a part of the account, without reading it as an address book:

* *Authentication* - `DavAuthenticator` splits the alias off before any other check: the password, the blocking counters and the onboarding are the ones of the login. The alias is kept in `DavContext.account_alias`. An empty login or alias, or an alias with a character refused in a login, is refused like a wrong password. `!` is always the separator: a login can never contain it.
* *Paths* - the principal of the account is `/dav/<login>!<alias>/`, and every path of its tree derives from it: `current-user-principal`, `principal-URL` and the homes keep the alias, so that macOS stays on the tree of that account.
* *Resolution* - an account with an alias only reaches the tree of that alias, an account without alias only the canonical tree. The alias of the path is compared as is, case included.

The alias is not checked at sign-in: an alias that is not the key of an address book of the user gives an account without address book, which discloses nothing.
The calendars of the account are not restricted: Calendar on macOS syncs several calendars per account.

[[business-model-properties]]
=== Properties of a business model

The properties of a business model are never built by hand: a serializer of `app/dav/serializer`, named `<Model>SerializerDavProps`, converts the model into its properties, by name in Clark notation.
These serializers belong to the DAV server:

* not to `app/manager/dav/protocol`, which knows no business model: they depend on the models and on the choices of the server (properties exposed), which a DAV client does not share;
* not to the modules, which return business objects and the formats of their domain (iCalendar, vCard), never DAV properties.

A model read through an interface is converted by that interface, with the serializer the resolver gives to its constructor: the interface returns DAV properties without depending on `app/dav`, its parameter being typed on the `Serializer` contract. The interface adds the values written in a format of the domain by a serializer of the module, as the time zone of a calendar.
The properties depending on the account and not on the model only, as the paths, are added by the resource.

* *CalCalendarSerializerDavProps* - Converts a calendar into the properties of its collection, given to `InterfaceDavCalendar` by the resolver (see <<calendars>>).
* *UserSerializerDavProps* - Converts the user of the `DavContext` into the properties of its principal, applied by `DavPrincipalResource`: its name (`displayname`) and its mail address followed by its aliases (`calendar-user-address-set`, as `mailto:` URIs), so that an invitation sent to an alias is matched to the principal. `alternate-URI-set` and `group-membership`, required by RFC 3744 section 4, are empty.

[[PROPFIND]]
== PROPFIND

`DavPropfindHandler` answers a PROPFIND (RFC 4918 section 9.1) with a multistatus, 207 in `application/xml`: one response for the resource of the path and, with `Depth: 1`, one for each of its members.

* *Depth* - `0` or `1`. `infinity`, which a request without `Depth` stands for, is refused with 403 and the condition `DAV:propfind-finite-depth` (`ERROR_DAV_PROPFIND_INFINITE_DEPTH`), as RFC 4918 section 9.1.1 allows: listing a whole tree would read every calendar and address book of the account. Any other value is malformed (RFC 4918 section 10.2) and answered 400 (`ERROR_DAV_DEPTH_INVALID`).
* *prop* - the properties asked: the ones of the resource in a 200 propstat, the other ones in a 404 propstat.
* *propname* - the names of all the properties of the resource, without their value.
* *allprop* - the properties defined by WebDAV (`DAV_ALLPROP_PROPERTIES`, RFC 4918 section 15), plus the ones of the include element. A request without body is an allprop. The other specifications ask not to return their properties in an allprop (RFC 3744, RFC 4791, RFC 6352, RFC 6638), and RFC 5397 leaves `current-user-principal` to the server: clients ask for them by name.

A property shows up once per resource, even when asked twice.

[[error-bodies]]
=== Error bodies

An error tied to a precondition or a postcondition of the protocol is answered with an XML body naming the condition (RFC 4918 section 16):

----
<D:error xmlns:D="DAV:"><D:propfind-finite-depth /></D:error>
----

A handler only raises its `RequestException`: the dispatcher looks the error up in its table of conditions, and writes the body with `DavErrorSerializerXml`. The other errors have no body.

== XML protocol

The XML of WebDAV, CalDAV and CardDAV is read and written in `app/manager/dav/protocol`, with the `xml.etree` module of the standard library: no DAV library. The package depends neither on Flask nor on the DAV server, so that a DAV client can reuse it.
As for the calendars and the contacts, the messages are models (`model/`) converted by serializers (`serializer/`): the DAV server builds and reads objects, never XML.
Element and property names use the Clark notation of ElementTree, `\{namespace\}name`, for instance `{DAV:}displayname`.

* *PropfindRequest* - The properties asked by a PROPFIND: all of them (allprop, with the extra ones of its include element), their names only (propname), or a list (prop).
* *DavMultistatus* - The responses of a multistatus, one *DavPropResponse* per resource: its path, the properties found with their value, the names of the missing ones. A value is a text, or a value written as child elements: *DavHrefs* (references to resources), *DavResourceType*, *DavComponentSet* (`comp` elements of `supported-calendar-component-set`), *DavPrivilegeSet* (`privilege` elements of `current-user-privilege-set`), *DavSupportedPrivilegeSet* (tree of *DavSupportedPrivilege* of `supported-privilege-set`, each one with its description and the privileges it aggregates).
* *DavError* - The body of an error response: the name of the condition the request failed (see <<error-bodies>>).
* *PropfindRequestDeserializerXml* - Reads a PROPFIND body. A PROPFIND without body asks for all the properties (RFC 4918 section 9.1). A malformed body, or a body declaring a document type, is refused with 400 (`ERROR_DAV_XML_INVALID`). The body is given to the parser by chunks of 4 KB, so that a document type stops the parse at the end of its chunk; expat bounds the expansion of the entities of that chunk. Unknown elements are ignored, as WebDAV requires for its extensions (RFC 4918 section 17).
* *DavMultistatusSerializerXml* - Writes a multistatus: for each resource, the properties found in a 200 propstat and the missing ones in a 404 propstat. An href is the percent-encoded path of the resource, `@` kept as is. The characters XML 1.0 forbids, as the control characters, are removed from the text values.
* *DavErrorSerializerXml* - Writes an error body: an `error` element holding the condition as an empty element (RFC 4918 section 16).

The namespaces get fixed prefixes (`D:` WebDAV, `C:` CalDAV, `CR:` CardDAV, `CS:` CalendarServer, `IC:` Apple iCal), which keep the logs of the clients readable. They are registered once, when the package of the serializers is loaded: ElementTree keeps them in a registry shared by the whole process.

== Authentication

DAV clients authenticate with HTTP Basic and send their credentials with every request: there is no session.
Every request is authenticated, OPTIONS included: `DavHandler.handle` calls the authenticator before `process`, so that no handler can skip it.
The REST API authenticates in a Flask middleware run before its views; the DAV server reduces Flask to a single route, and the base handler plays that role.

[cols="1,3"]
|===
| Case | Answer

| Connection without TLS
| 403, without challenge. Basic credentials travel in clear: RFC 4918 section 20.1 forbids both using them and sending the Basic challenge on an insecure connection.

| Credentials missing, malformed or refused
| 401 with `WWW-Authenticate: Basic realm="SOGo", charset="UTF-8"`, so that the client asks for the password again.

| Login altering the user source queries, empty password
| 401, like a wrong password, before the user source is queried. See <<login-checks>>.

| Login blocked after too many wrong passwords
| 429, before the user source is queried, even with the right password. See <<login-blocking>>.

| Domain authenticated by an identity provider (`SOGO_D_AUTH_TYPE` other than `plain`)
| 403, before the user source is queried. The user source password would bypass the provider and its second factor.
Checked again with the domain of the account found in the user source, when it differs from the domain of the login: the password has then been checked, and the refusal is answered 401 and counted like a wrong password, so that the answer does not tell whether the password is right.

| Login refused by the domain rules (no domain while `SOGO_S_DOMAINLESS_LOGIN` is off, unknown domain while `SOGO_S_REJECT_UNKNOWN_DOMAIN` is on)
| 401, like a wrong password, before the user source is queried. `ModuleAuth` raises this refusal without error code: the web sign-in answers it 500, that DAV clients would not take for a wrong login.

| User who never signed in
| Onboarded by its first request, like at the first web sign-in: profile, personal calendar and address book, special mail folders. See <<onboarding>>.

| Onboarding running in another request for more than 10 seconds
| 503, so that the client tries again. See <<onboarding>>.
|===

The credentials are checked against the user sources on every request, like the REST API does for the user of a voucher: `DavAuthenticator` calls `InterfaceAuthUser.check_user`, then `InterfaceAuthUser.onboard_user_and_fill_info` once the domain of the account is checked.
Logins with or without domain follow the same rules as the web sign-in.
There is no cache: a password changed or an account disabled in the user source is refused from the next request on.

[[onboarding]]
=== First connection

A user can add the account to a client before ever signing in to the web interface. The first request onboards the user like the first web sign-in, with the same code (`InterfaceAuthUser.onboard_user_and_fill_info`): profile, personal calendar and address book, special mail folders.
The onboarding comes after the check of the domain of the account: an account whose domain refuses passwords is not onboarded, and its password is not sent to the mail server. The DAV server onboards with the settings of the domain of the account.

Every request, DAV or web sign-in, reads the profile first. Its folders are set once the personal calendar and address book exist: with folders, the request goes on without reading the lock.

Clients adding an account often send several requests at once. The onboarding runs under a Redis lock per user (`onboarding_lock:<login>`, `SET NX`, 60 seconds): the other requests of the user wait until it is released, checking every 0.2 seconds, and give up after 10 seconds with `ERROR_LOGIN_ONBOARDING_RUNNING` (503).
The time to live frees the lock of a worker killed during the onboarding: it is longer than the gunicorn worker timeout (30 seconds by default).

Known limits, rare cases left as is:

* An onboarding failing once the profile is created is not resumed, like at the web sign-in: the profile keeps no folders, and each request of the user then reads the lock.
* A request losing the race for the lock waits for the request holding it: if that one fails before creating the profile, the waiting one fails as well. The next request onboards the user.
* The lock key is the login as sent: two spellings of an account differing by their case do not share it.
* The lock is released by a read then a deletion, not atomically.
* Waiting requests hold their worker, up to 10 seconds.

[[login-checks]]
=== Login and password checks

The login is inserted in the LDAP filters and DNs, and in the SQL queries of the user sources. Before they are queried, `DavAuthenticator` refuses the logins with:

* a space: LDAP ignores the spaces around a value, while the domain settings are looked up with the exact domain name;
* a non-printable character: control, invisible (zero width space, soft hyphen...);
* a leading `#`: a DN value starting with it is read as hexadecimal BER (RFC 4514 section 2.4), another spelling of the same account with its own counters;
* a character of `DAV_LOGIN_FORBIDDEN_CHARS`: the characters of the LDAP filters and DNs `* ( ) \ , = ; < > "`, as a wildcard would test the password against another account, and `/`, as the login is a segment of the path of the principal of the user, `/dav/<login>/` (see <<Resources>>);
* more than one `@`.

`!` never reaches these checks: it separates the login from the alias of the account (see <<account-alias>>), the login is the part before it.

`+` is accepted on purpose, for subaddresses (`alice+tag@example.org`), although it separates the values of an LDAP DN: such logins only work with SQL user sources and with LDAP sources that search the DN of the user (`US_LDAP_BIND_FIELD`). When the DN is built from the login, the bind fails.
The domain part of the login is lowercased: domain names ignore case (RFC 4343), the domain settings are looked up with the exact name. The local part is kept as is.

The password is never altered nor filtered, it can hold any character, colons included.
Only the empty password is refused: LDAP takes it as an unauthenticated bind request (RFC 4513 section 5.1.2), that some directories (Active Directory by default) grant without checking anything.

[[login-blocking]]
=== Blocking after wrong passwords

A login is blocked for `SOGO_D_LOGIN_CHECK_BLOCK_TIME` seconds (300 by default) once `SOGO_D_LOGIN_CHECK_MAX_ATTEMPT` distinct wrong passwords were sent, each within `SOGO_D_LOGIN_CHECK_TIME_SPAN` seconds (600 by default) of the previous one.
These are the authentication settings of the login domain, read before the block is checked. `SOGO_D_LOGIN_CHECK_MAX_ATTEMPT` at 0, its default value, turns the blocking off.

* *Distinct passwords* - a device still sending an old password counts once, and does not block the account in a loop.
* *No reset on success* - a client syncing every few minutes would clear the count before an attacker reaches the limit.
* *Blocked login* - answered 429 without querying the user source, even with the right password: the brute force cannot go on during the block. A 401 would make the client ask the password again, in vain.
* *Login variants* - the counters are shared by the variants of a login that the user sources take as the same (case, accents, Unicode compatibility forms): the default MariaDB collations ignore accents, `álice@example.org` finds the account `alice@example.org`.
* *What counts* - the refusals of the user source, and the password refused by the domain of the account. Malformed credentials and 403 answers do not count.
* *Account alias* - the counters are the ones of the login, without its alias: changing the alias at each try does not escape the block.

`DavLoginLimiter` keeps, per login, a Redis hash whose fields are keyed fingerprints of the wrong passwords (HMAC-SHA256, key derived from `SOGO_AES_ENC_KEY`): a dump of the cache gives away neither the wrong passwords, often typos of the right one, nor a way to brute-force them.
Each wrong password adds its field with one `HSET`: requests sent in parallel never overwrite each other's fingerprints, which a read then write of a list would do. Each one also restarts the time to live of the hash.
When Redis is unreachable and the blocking is on for the domain of the login, DAV requests fail with a 500 error, like the REST API whose sessions live in Redis: passwords are never tried without the counters.
With the blocking off, the requests of an onboarded user do not use Redis. The onboarding of a user needs Redis for its lock whatever the blocking: without Redis, the requests of a user who never signed in, or whose onboarding failed, fail with a 500 error.

The block is checked before the user source is queried and set after the refusal: requests sent at the same time all pass the check before the block is set.
The overshoot is bounded by the number of requests the DAV server processes at once, one per gunicorn worker (`GUNICORN_WORKERS`) and per container.

Anyone knowing a login can block the DAV access of that account. The block only applies to the DAV server: the web sign-in reads neither these counters nor the `SOGO_D_LOGIN_CHECK_*` settings.

=== Request context

Handlers receive a `DavContext`: process and system settings, settings of the user domain, the user filled with its directory info and profile, the cache client of the worker, and the alias of the login, if any.
The user keeps the password in memory, for the mail servers.
Handlers pass it to `DavResourceResolver`, which builds `InterfaceDavCalendar` from it, with the process settings, the user and the cache client, along with the serializer of the calendar properties and the name of the default calendar (see <<Resources>>): a handler never builds an interface.
The cache client comes from `sogo_cache()`, called by `DavHandler.handle`: one client per worker, shared by all its requests and threads, never closed by a request. It runs without the client side cache of redis-py, which is not thread-safe.

== Flask behaviours turned off

DAV clients trip on three defaults that suit web applications:

* *Automatic OPTIONS* - Flask answers OPTIONS itself, without the `DAV` header clients look for. The routes disable it so that `DavOptionsHandler` answers.
* *Trailing slash redirects* - clients address a collection with or without its trailing slash. Strict slashes are disabled, so both forms reach the same handler without a redirect.
* *HTML pages* - errors raised by Flask (unknown path or method, oversized body, unexpected exception) are answered without body. Responses without body carry no `Content-Type`.

Unexpected exceptions are not caught by the dispatcher: Flask logs them and answers 500.

== Running

Development, on the Werkzeug server (port 5001 by default, so that it runs next to `poetry run start`).
It has no reverse proxy in front of it and accepts Basic authentication over plain HTTP:

[source,bash]
----
poetry run dav
poetry run dav --port 5001 --no-debug
----

Production, with gunicorn and the same settings file as the REST API (`app/gunicorn.conf.py`):

[source,bash]
----
gunicorn -c app/gunicorn.conf.py app.dav.run_server:app
----

| `poetry run gunicorn -c app/gunicorn.conf.py app.dav.run_server:app`

The `GUNICORN_*` variables (`GUNICORN_WORKERS`, `GUNICORN_BIND`...) are set per container. Like the REST API, the master checks the database and the cache once before starting the workers (`init_once`), and each worker reads the configuration state at start-up: a SOGo configured afterwards needs a restart of the DAV server.

The reverse proxy routes `/dav/`, `/.well-known/caldav` and `/.well-known/carddav` to the DAV container, everything else to the REST API.

=== Reverse proxy and TLS

The reverse proxy terminates TLS.
The DAV server learns that the client used https from the `X-Forwarded-Proto` header, which gunicorn only trusts from the addresses listed in `FORWARDED_ALLOW_IPS` (`app/gunicorn.conf.py`, `127.0.0.1,::1` by default).
For the dav container:

* set `FORWARDED_ALLOW_IPS` to the address of the reverse proxy;
* make the proxy overwrite `X-Forwarded-Proto` instead of passing on the header sent by the client (nginx: `proxy_set_header X-Forwarded-Proto $scheme;`);
* expose `/dav/` and the well-known URIs over https only.

Without `FORWARDED_ALLOW_IPS`, every authenticated request is answered 403.
